## Slide 3 — Technical Architecture Flowchart

Documents enter the system from six sources: PDF files, scanned PDFs, Excel spreadsheets, CSV files, images, and web scraping from coal.gov.in. All sources flow into the Ingestion Engine which uses PyMuPDF for spatial text extraction with bounding box coordinates, Tesseract OCR for scanned documents, and openpyxl for spreadsheets. The Ingestion Engine outputs to the Chunking layer which creates 400-word sliding window segments with 50-word overlap, preserving page numbers and bounding box metadata. Chunks then flow to two parallel paths: first to 384-dimensional vector embedding generation which stores into ChromaDB persistent vector store, and second to BM25 keyword index for exact term matching. When a user submits a query, it triggers Hybrid Retrieval that combines ChromaDB vector similarity search with BM25 keyword re-ranking. The top relevant chunks with their source metadata flow to the Groq LPU inference engine which has a 14-model cascade: LLaMA 3.3 70B as primary, then Qwen 2.5 32B, Mixtral 8x7B, Gemma2 9B, and others as fallbacks. If all API models fail, a local extractive fallback engine takes over. The inference output is an AI answer with structured citation objects containing source filename, page number, and bounding box coordinates. This output feeds three user-facing modules: the Split-Screen Q&A Assistant with PDF viewer and amber bounding box overlays, the Report Studio generating PDF DOCX and Markdown, and the Analytics Dashboard with interactive word cloud and subsidiary charts.

## Slide 3 — Architecture Priority Hierarchy

The system has three priority layers for inference. The primary layer uses Groq LPU hardware with Meta LLaMA 3.3 70B, providing the highest quality answers with under 500 millisecond latency. If this model is rate-limited or unavailable, the system drops to the secondary layer which sequentially tries 13 alternative models including Qwen 2.5 32B, LLaMA 3.1 70B, LLaMA 3.1 8B, Mixtral 8x7B, Gemma2 9B, and LLaMA3 8B using exponential backoff and retry. If all 14 API models are exhausted, the system drops to the tertiary layer which is a fully offline local extractive engine using BM25 and TF-IDF summarization. This guarantees the system never returns empty and maintains 100 percent uptime regardless of API availability.

## Full System Flowchart — Master Description

GeoIntel Core is an AI-powered geological and mining reporting platform for CMPDI and Coal India Limited subsidiaries. The system has four stages. Stage 1 is Ingestion and Extraction where documents from six sources enter the system: typed PDFs, scanned PDFs processed through Tesseract OCR, Excel spreadsheets parsed by openpyxl, CSV files, photographic images with OCR, and live web scraping from coal.gov.in using httpx and BeautifulSoup. PyMuPDF extracts text with exact page numbers and spatial bounding box coordinates. Stage 2 is Indexing and Knowledge Base where extracted text is split into 400-word sliding window chunks with 50-word overlap preserving all spatial metadata. Each chunk is converted to a 384-dimensional vector embedding and stored in ChromaDB persistent vector store with cosine similarity search. Simultaneously a BM25 keyword index is built for exact term matching of domain vocabulary like Barakar, stripping ratio, and GCV. Stage 3 is Resilient Inference where a user query triggers hybrid retrieval combining ChromaDB vector search with BM25 re-ranking to find the most relevant chunks. These chunks with their source metadata are sent to Groq LPU hardware for inference using a 14-model cascade starting with LLaMA 3.3 70B and falling back through 13 alternatives to a local extractive engine if all APIs fail. The output is a structured answer with citation objects containing source filename, page number, bounding box coordinates, and exact text snippet. Stage 4 is Presentation and Synthesis with three modules: the Q&A Assistant showing a split-screen interface with the AI answer on the left and the source PDF on the right with amber bounding box overlays on cited text, the Report Studio where users select report type subsidiary and timeframe then add custom directives to generate publication-grade PDF DOCX and Markdown reports with factual audit confidence scores, and the Analytics Dashboard displaying an interactive word cloud with in-place occurrence inspector, subsidiary production charts comparing target versus actual, topic clusters, and KPI cards. The entire system deploys via a single Docker Compose command and runs on standard office hardware with no GPU required.
